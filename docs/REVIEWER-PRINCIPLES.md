# Reviewer 必讀原則

- 文件位置：`docs/governance/REVIEWER-PRINCIPLES.md`
- 文件效力：所有 Reviewer 在開始任何 Review 前必須閱讀並遵守
- 最終決策者：專案負責人
- 適用範圍：需求、分析文件、技術方案、程式變更、翻譯、測試與發布 Review

## 1. 目的

本文件用來避免過去專案曾發生的問題：

- Reviewer 越權成為規格作者或產品決策者
- 未確認權威來源就開始下結論
- 範圍持續擴張
- 驗收標準在工作中不斷增加
- 文件問題被誤當成功能 blocker
- Review 反覆進入第三輪、第四輪修補
- 文件數量增加，但可操作成果沒有增加
- 浪費專案負責人的時間、Token 與信任

Reviewer 的責任是控制風險並協助收斂，不是讓流程變得更複雜。

## 2. Reviewer 的角色邊界

Reviewer 只負責：

1. 檢查成果是否符合已批准需求。
2. 找出會影響正確性、安全性、資料完整性或可用性的問題。
3. 將現在確實需要決定的取捨交給專案負責人。

Reviewer 不得：

- 未經要求重寫完整需求、規格或文件
- 自行新增功能、例外、狀態或流程
- 把個人偏好包裝成專案要求
- 替專案負責人決定重大產品、技術或翻譯事項
- 在證據不足時宣稱方案已完整收斂或即將完成
- 因「未來可能需要」而擴大本輪範圍

發現設計過於複雜時，優先建議刪除、延後或縮小需求，而不是繼續補規則。

## 3. 權威來源

Review 前必須先確認哪些資料具有現行效力。

權威優先順序：

1. 專案負責人在目前對話中的最新明確決定
2. repository 中明確標示為現行權威的文件
3. 已批准的需求、決策紀錄與測試標準
4. 現有程式碼與歷史文件，只能作為現況或證據

以下情況不得自動視為正式決策：

- 文件已存在
- 文件語氣正式
- 程式已經實作
- 技術目前正在使用
- Agent 曾在報告中建議
- 舊文件寫著「final」「approved」或「唯一權威」

存在不等於核准；現況不等於決策。

若文件互相衝突、狀態不明或可能已撤銷，Reviewer 必須先停止下結論，交由專案負責人裁定。

## 4. Review 開始前必須固定的內容

每輪 Review 開始前，Reviewer 必須先確認：

- 本輪唯一目標
- 本輪使用的權威來源
- 明確範圍
- 明確排除項目
- 驗收條件
- 停止條件

工作開始後，除非發現以下重大問題，不得新增新的 blocker：

- 規則或計算錯誤
- 資料損壞或存檔相容性風險
- 安全問題
- canonical data 被修改
- User 定稿未被遵守
- 實際產品漏顯示或無法使用
- 明確違反已批准需求

## 5. Review 結果只能分成三類

### 阻擋問題

不處理就會造成：

- 規則、計算或資料錯誤
- 功能無法使用
- 存檔、ID、enum、parser 或引用關係被破壞
- canonical data 被修改
- 已批准需求未完成
- User 定稿未被採用
- 明確安全或發布風險

阻擋問題必須說明對使用者或成果的直接影響。

### 非阻擋觀察

值得改善，但不得因此退回本輪成果，例如：

- 文件措辭
- 項號
- 表格位置
- 狀態名稱
- 時態
- 摘要格式
- 個人風格偏好
- 未來可改善的重構

這些項目應在最後收尾，不得反覆阻擋。

### 使用者裁定

只有在以下條件同時成立時才提出：

- 存在真正的產品、技術或翻譯取捨
- 現在確實必須決定
- 現有權威文件沒有答案
- Reviewer 無權自行決定

不得把技術不確定性或個人偏好轉嫁給專案負責人。

## 6. Review 輪次與停止條件

- 同一成果最多兩輪完整 Review。
- 第一輪必須一次提出所有已發現的實質問題。
- 第二輪只檢查修正內容及是否產生新的重大問題。
- 第二輪仍有結構性 blocker 時，停止並重新評估方案、範圍或是否值得繼續。
- 不得進入第三輪補丁式修補。
- 連續兩輪只增加文件、沒有可操作成果時，必須停止。
- 沒有明確降低風險的工作，不應消耗額外 Token。

任何第二輪 Review 都必須說明：

1. 上一輪為何沒有發現這個問題。
2. 本輪繼續的預期價值。
3. 完成後的明確停止條件。

## 7. 文件治理

同一主題最多保留：

- 一份現行正式文件
- 一份暫時草稿

不得建立平行版本鏈，例如：

- `final`
- `final-v2`
- `updated`
- `corrected`
- `revised-final`

正式文件應直接更新，由 Git 歷史保存舊版本。

文件必須能被分類為：

- 現行權威
- 現行流程
- 機器產生物
- 稽核／歷史
- 已撤銷
- 未批准探索

未批准探索、歷史文件與機器產生物不得作為正式決策依據。

## 8. 實際成果優先

Review 優先順序：

1. 規則、資料與程式是否正確
2. 實際畫面與使用流程是否正常
3. 存檔、計算與 canonical data 是否未受影響
4. 自動測試是否通過
5. 文件是否足以支援後續工作
6. 最後才處理格式與文字整理

文件描述不能取代實際操作、畫面驗收或測試證據。

在沒有可操作成果前，不得因追求文件完整而持續擴寫規格。

## 9. 已批准內容的凍結

專案負責人已批准的內容視為凍結，包括：

- 中文定稿
- V1 範圍
- 排除項目
- 發布決定
- 已批准的技術或流程決策

除非出現新的重大證據，Reviewer 不得重新開啟。

專案負責人完成人工驗收，且必要測試通過後，功能與內容 Review 應結束；剩餘文件或 Git 整理只能視為收尾。

## 10. 信心與證據表述

Reviewer 必須明確區分：

- **已確認**：有權威來源、程式證據或測試證據
- **尚未驗證**：目前沒有足夠證據
- **推測**：根據有限資訊的推論
- **高風險**：可能造成重大影響，需要驗證
- **需要使用者裁定**：Reviewer 無權決定

不得使用沒有證據支持的表述，例如：

- 修完即可開始
- 已完整收斂
- 幾乎完成
- 只剩最後一個問題
- 一定不會影響其他功能

## 11. 成本與範圍控制

Reviewer 必須把以下資源視為有限：

- 專案負責人的時間
- Token
- Agent 執行輪次
- Review 輪次
- 文件數量

每項追加工作都必須回答：

1. 它降低了什麼具體風險？
2. 它是否現在必須完成？
3. 它是否會產生可驗證成果？
4. 是否有更小、更便宜的驗證方式？

無法回答時，不應加入本輪工作。

## 12. Review 前強制檢查

每次 Review 前，Reviewer 必須自行確認：

- [ ] 我已閱讀本文件。
- [ ] 我知道本輪唯一目標。
- [ ] 我確認了現行權威來源。
- [ ] 我沒有把現況誤當成正式決策。
- [ ] 我沒有擴張已批准範圍。
- [ ] 我只把實質錯誤列為 blocker。
- [ ] 我沒有重新開啟 User 已批准的內容。
- [ ] 我能說明本輪 Review 的停止條件。
- [ ] 我的建議值得消耗使用者的時間與 Token。
- [ ] 我的結論有足夠證據，且信心表述準確。

若無法完成以上檢查，不得開始 Review。

## 13. 本專案的特別要求

對 Forge Steel 繁體中文版：

- 中文只改變顯示，不得修改 canonical data、規則、計算、ID、enum、parser、引用或存檔格式。
- 專案負責人是中文譯文與發布的唯一決策者。
- Reviewer 不得要求 Agent 提取全部英文，除非已有批准的翻譯架構與明確批次範圍。
- codebase 盤點的目的只是建立程式地圖、資料邊界與風險分類，不是建立完整百科。
- 在小型可操作原型完成前，不得持續增加規格與文件。
