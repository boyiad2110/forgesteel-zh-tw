# 一批只記一次

原 PR 保存完整範圍、來源、驗證證據、人工驗收與合併結果。Sheet 只記必要狀態。交付驗收前，同一批更新 repo 文件。PROGRESS 留已交付範圍、驗證版本與 PR 連結；驗收與合併狀態以原 PR 為準。已交付的 TODO 改由 PROGRESS 的 PR 索引追蹤。驗收結果與合併 SHA 只在發生後回寫原 PR 與 Sheet，不另開只改文件的提交，也不預寫「已驗收」。既有歷史紀錄不改寫。

## 執行與合併順序

1. 確認 Git 狀態、保留既有修改。一般內容批次有兩道人工關卡：實作前的範圍／翻譯核准，以及交付後的人工驗收。使用者明示要分段驗收時，仍照該要求執行，執行者不能自行取消。
   範圍核准前先列「內容欄位 × 玩家旅程位置」覆蓋清單。每格標出來源 ID、原文版本與狀態：應顯示核准中文、未核准保留英文、動態未支援保留英文、依規則保留原文、不適用。已有核准來源卻未接線須列為缺漏，不能標完成。動態句、改名、自訂及未知來源另列預期回退，避免把有 mapping 誤認為每個畫面都已接線。
2. 已核准範圍內，盤點、實作、測試修正與必要文件整理由執行者自行完成。核准譯文的 Sheet 寫入依 SNAPSHOT 先讀、精準寫入並回讀。只有新譯文、擴大範圍、改變既有決策，或規則無法解決的阻塞，才再詢問。
3. 同一份未再變更的版本依 RULES 跑一次完整驗證。程式、翻譯資產或相關設定再變更時重新驗證；定位失敗可跑相關單檔測試，單檔結果不能當成整體通過。同程式版本只改文件時，引用該版本既有驗證，只檢查文件 diff、連結與一致性。
4. 交付前在同一批更新 PROGRESS、TODO、README 與仍有效決策中的目前狀態。PROGRESS 記已交付範圍、驗證版本與 PR 連結；完成項從 TODO 未完成表移出，改由該 PR 索引追蹤。此時不寫驗收或合併結果。交付同一 PR，並附具體驗收位置。
   對清單中每個「應顯示核准中文」的位置提供可重跑的顯示測試或實際操作結果；至少核對正體中文與英文切換。共用元件只須測一次，但要列出實際共用該元件的位置。用 `node scripts/l10n/coverage-report.mjs` 檢查六個位置的分類，完整語系守門也會執行這項檢查。報告只驗清單結構，不能替代 Vitest、瀏覽器及人工核對。未覆蓋的格子明列限制，不以單一畫面通過推論整段旅程完成。
   若驗收或測試找到漏接，先修該位置，再追同一共用元件在本批其他位置的用途，補能抓到此類漏接的回歸後重跑完整驗證。
5. 人工驗收完成後，把實際驗收結果寫回原 PR；需要時依 SNAPSHOT 把必要狀態精準寫入 Sheet 並回讀。不為驗收另開文件提交，repo 文件不補寫「已驗收」。
6. 等最新 head 的必要 CI 成功，再確認 base 是 develop、驗收授權適用於本批、合併方式正確。一般內容／工具改善用 squash；上游同步用 merge。合併要求 head 未變，不能忽略新增提交或繞過必要檢查。自主合併須有適用於該批的明確授權。
7. 合併後只把實際 merge SHA 與合併結果補到原 PR 與 Sheet。不為合併 SHA 另開文件提交，不改寫已合併歷史。同步本機 develop 前再確認工作目錄。

GitHub CLI 一律指定 repo；合併命令範例（先完成上述核對）：

```powershell
gh pr view <PR> --repo boyiad2110/forgesteel-zh-tw --json baseRefName,headRefOid,state,isDraft,statusCheckRollup
gh pr checks <PR> --repo boyiad2110/forgesteel-zh-tw
gh pr merge <PR> --repo boyiad2110/forgesteel-zh-tw --squash --match-head-commit <已核對的完整HEAD>
# 只有上游同步 PR 將 --squash 改為 --merge
```

## 結案
交付時寫範圍、驗證程式版本與限制，不預寫「已驗收」或未知 merge SHA。
人工驗收後把實際結果補進本 PR；合併後只在本 PR 補實際合併方式與 SHA。必要 Sheet 狀態另依 SNAPSHOT 寫入並回讀。
